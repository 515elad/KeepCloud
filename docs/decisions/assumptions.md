# Assumptions log

Where the PRD is unclear, the simplest choice that keeps the intent is recorded here. Open decisions (D-xx, SD-xx, UX-Dx) are not decided here: their stated default is implemented and labelled "pending decision" in the UI when the feature appears.

| # | Phase | Topic | Assumption | Why |
|---|---|---|---|---|
| A-01 | 0 | Repository | The repo is `github.com/515elad/KeepCloud`, not `5liftoff/KeepCloud` as in the brief. | The owner gave this repo after the original could not be created from the session. |
| A-02 | 0 | Existing foundation | There is no existing gateway, policy store, observability stack or fixtures to reuse. Everything is built new in this repo. | The repo was empty. See `docs/architecture/verification.md`. |
| A-03 | 0 | Python version | Project targets Python 3.12 (PRD). The Docker image and CI use 3.12. | PRD v1.4 Section 2.3. |
| A-04 | 0 | Navigation | The eight pages in the owner brief are built. The "Spend" area from UX-1 is added in phase 4, when the brief introduces the Spend page. | The brief's phase 0 list has no Spend page; phase 4 does. |
| A-05 | 0 | "Coming in phase N" | A page can have several sections that arrive in different phases. Each section shows its own phase and requirement IDs. | The Gateway page, for example, gets the registry in phase 1 and denials in phase 2. |
| A-06 | 0 | Health strip items | Gateway, Policy sync, Ledger, Egress, Alerting, Data sources (UX-6). Egress control (FR-20) is not in any MVP phase, so Egress stays Unknown for the whole MVP and the UI says so. | Showing it as anything else would claim a control that does not exist (PRD v1.5 Section 1). |
| A-07 | 0 | Health thresholds | Healthy up to 60 s since the last heartbeat, Degraded up to 180 s, then Failing (policy sync 30 s / 60 s; data sources 24 h / 48 h). A heartbeat dated in the future gives Unknown. | The PRD sets no heartbeat thresholds. Policy sync follows the 30 s snapshot rule in FR-18. Values are in one place (`keepair.health.COMPONENTS`). |
| A-08 | 0 | Failure visibility | Phase 0 failures produce a metric, an alert record and a UI row (owner brief, hard rule 5). The audit record that SEC-36 also asks for is added when the audit log is built in phase 6. | The audit log is a phase 6 deliverable. |
| A-09 | 0 | Alerts during a database outage | If the database is down, an alert cannot be stored there. It is held in memory, shown in the UI as "held in memory", and written to the database when it returns. Alerts held in memory are lost if the process restarts during the outage; the metric is not. | A failure of the store must still be visible. An external alert sink arrives with the outbox (v1.4 S5). |
| A-10 | 0 | Tenancy | Phase 0 tables (heartbeats, alerts, app_meta, demo_placeholder) are system tables with no `tenant_id`. Tenant tables and row-level security (SEC-16) start with the first tenant-owned data in phase 1. | No tenant data exists yet. |
| A-11 | 0 | Sign-in | Phase 0 has no sign-in. The app binds to localhost in docker compose. Local accounts and TOTP arrive in phase 5 as the brief orders. | Brief phase order. Not for exposure to a network before phase 5. |
| A-12 | 0 | "i" for non-calculated fields | Fields that are recorded, not calculated, show "Formula: None" and an example value. Only calculated fields must have a formula and a code-checked worked example. | A formula for a recorded value would be invented. |
| A-13 | 0 | "i" on the health strip | The strip has one "i" for Status, not one per component, since the six chips are the same field. The Overview table repeats each component with full columns. | Six identical buttons in the header would add noise without information. |
| A-14 | 0 | Demo clock vs. app clock | The seed uses a fixed clock (2026-01-15 09:00:00 UTC). The running app uses the real clock for new events such as alerts. | Seeded data must be identical on every run; live events must carry the real time. |
| A-15 | 0 | Open-source action pinning | CI actions are pinned to commit SHAs (SEC-46). | Resolved from the upstream tags on 2026-11-19. |
| A-16 | 1 | Independent and subdivision budgets (FR-04) | The limit path of a budget is the budget itself, then each parent reached while the budget below it is a Subdivision. An Independent budget ends the path: its parent does not limit it. `effective_remaining` is the lowest remaining amount among the Hard-limit and Approval budgets on that path, and "No enforced limit" when there is none. | The PRD says an independent budget "does not contribute its parent's remaining to its own cap" and a subdivision "is checked against all ancestors". This is the simplest reading that satisfies both named tests. |
| A-17 | 1 | Where spend is recorded | Spend on a budget is also recorded on every other budget of its limit path. Spend on an Independent budget is not recorded on its parent. | Without this, a parent's counters would rise with no check, and its remaining amount could go below zero. An organization-wide total across independent budgets belongs to reporting (phase 4), not to the limit counters. |
| A-18 | 1 | Currencies in a hierarchy | A Subdivision budget must use its parent's currency. Budgets in another currency are Independent. | No FX conversion exists in the MVP (v1.4 Section 6, multi-currency, is later work). |
| A-19 | 1 | Editing budgets | Budgets are read-only in phase 1 and come from the demo seed. Creating and editing budgets needs owners and sign-in (phase 5). | The brief titles the phase "budgets and policy visibility" and places owners and accounts in phase 5. |
| A-20 | 1 | Hard limits without owners | Demo budgets with a Hard limit have no owner yet. The rule "no hard limit without an active owner" (FR-17) is enforced in phase 5, when owners exist. Nothing is enforced on any budget until the gateway exists (phase 2). | Owner accounts are a phase 5 deliverable. |
| A-21 | 1 | Blocking from the UI | Adding a block works now, needs a reason, and is recorded with actor `demo-operator`. Lifting a block is disabled until the two-person flow of phase 5; the only undo in the demo is reloading the demo data. | FR-18: any administrator may add a block in one step; lifting needs two people. Adding only narrows access, so it is safe before sign-in exists. SD-03 is pending; its default (no override) is what is built. |
| A-22 | 1 | "Tooltip" for the locked switch | The reason a model's switch is locked is shown as visible text next to it, and also as a tooltip on hover. | A disabled control cannot take keyboard focus, so a tooltip alone would hide the reason from keyboard and screen-reader users (UX-14). |
| A-23 | 1 | Registry change history | Status changes are stored in `registry_changes` (who, when, why). The hash-chained audit log of phase 6 will record them as well. | UX-3 needs "last change" now; the audit log is a phase 6 deliverable. |
| A-24 | 1 | Registry scope | Vendors, models and aliases are per tenant. | SEC-16 puts `tenant_id` on every tenant table, and a block is a tenant's decision. |
| A-25 | 1 | Row-level security | Tables carry `tenant_id` and every query filters on it, but PostgreSQL row-level security is not switched on yet. It arrives with sign-in in phase 5, when a tenant context exists to bind it to. There is one tenant until then. | SEC-16 sets the tenant context "only after authentication", which does not exist yet. |
| A-26 | 1 | Bar precision | The bar is drawn in whole percent (a reservation is rounded up to 1% so that it stays visible). The exact values, to two decimals, are in the text under the bar. | Segment widths come from fixed style classes, because the Content-Security-Policy forbids inline styles (SEC-27). |
| A-27 | 1 | Forecast band | The forecast band on the budget bar (UX-8, UX-D7) is not built: there is no spend history to forecast from. | Spend history starts in phase 2. Not in any phase of the brief; listed for the final "not built" list. |
| A-28 | 1 | Unregistered models | Names requested but not registered are kept in their own table and shown as Unregistered. D-03 (discovery in monitor scope) is pending; requests for them are denied (FR-18 default deny). "Register model" is shown disabled until phase 2. | UX-4 asks for three separate labels. |
| A-29 | 2 | Approval policy (FR-05, FR-11) | When a project's own budget has the Approval policy, every request from that project is held: budget is reserved, nothing is sent, and the agent gets HTTP 202 with code `APPROVAL_REQUIRED`. Parent budgets with the Approval policy act as caps, like hard limits. Approving or rejecting a hold is phase 5; until then a hold expires after 24 hours and its budget is released. | PRD v1.4 says a HELD reservation "reserves budget" and is the outcome of the approval policy, so a hold must fit the cap. D-07 default: the request body is not stored. |
| A-30 | 2 | Unknown models (D-03) | Unknown models are always denied, also for monitor-only budgets. The name is recorded under "Unregistered models". | The owner brief (hard rule 7) says unknown models are denied. D-03's default would allow them in monitor scope; that decision is pending and the stricter rule is built. An unknown model also has no price to estimate from. |
| A-31 | 2 | Streaming | Streaming requests (`"stream": true`) are refused with 400 `STREAMING_NOT_SUPPORTED`. | Not in the brief's phase 2. Refusing keeps bypass route B-h closed: no stream, no way to dodge settlement. Listed as not built. |
| A-32 | 2 | Stored result for idempotent replay | The response of a finished request is kept for 24 hours so that a retry with the same key gets the same result. Prompts are never stored. Keys left "in flight" by a crash are removed after 10 minutes. | "Same key, same body returns the stored result" needs the result. SEC-25 (no responses stored by default) is narrowed by this 24-hour copy; the owner may prefer a shorter window. |
| A-33 | 2 | Provider failures | A timeout or connection error after dispatch settles at the reserved amount with usage unknown (PRD). An HTTP error answer from the provider releases the reservation and returns 502; the provider's error text is not passed on. An answer without usage figures settles at the reserved amount. | The PRD defines the timeout case only. A provider that answers with an error did not do the work. |
| A-34 | 2 | Token and policy caching | Credentials are looked up in the database on every request (no 30-second cache), so revocation is immediate. The policy snapshot is reloaded by polling at most every 5 seconds, not by LISTEN/NOTIFY; older than 30 seconds without a successful reload denies everything. | Simplest design that meets "revoked within 30 s" and "block effective within 5 s". The cache can be added if pilot latency needs it. |
| A-35 | 2 | Currency conversion | Model prices are in USD in the demo. A budget in another currency is charged through a stored rate (`fx_rates`, one invented demo rate USD to EUR 0.92). Conversion rounds up. No rate means the request is denied (`FX_RATE_MISSING`). | Without this no EUR budget could be used. PRD v1.4 Section 6 (multi-currency) describes the table. |
| A-36 | 2 | Demo credentials | Demo tokens are derived from the demo seed, so the traffic generator can present them without any token being stored. They are issued when the demo data is loaded, using the database clock (valid 90 days), outside the fixed-clock seed. The gateway refuses to start in production on a database that holds demo data. | A credential's lifetime is real time, but the seeded data set must be identical on every run. |
| A-37 | 2 | Seeded reserved amounts | Each seeded "reserved" amount is backed by a seeded open reservation with a fixed far expiry. They stand for long-running requests and are never swept. | The ledger invariant (a budget's reserved amount equals its open reservations) must also hold for demo data. |
| A-38 | 2 | Demo traffic | The 500 requests, their order and their outcomes are fixed by the seed, and so are the resulting budget totals. Timestamps and request IDs are real. Sending the same run again replays stored results. | The requests go through the live gateway, whose clock is real time. |
| A-39 | 2 | Decision record instead of audit and outbox rows | For an allowed or held request the decision row is written in the reservation's transaction: no record, no dispatch. The hash-chained audit row and the outbox row that PRD v1.4 Section 2.5 also asks for arrive in phase 6. Requests refused with 401 are counted in metrics only, because no tenant is known. | The audit log is a phase 6 deliverable. |
| A-40 | 2 | Vault | Provider keys come from a `Vault` interface. The MVP implementation returns a fixed non-secret value for the mock provider. No KMS exists. | Hard rule 1: no real credentials. |
| A-41 | 2 | Ledger outage | When the ledger cannot be reached, every request is refused with 503 `LEDGER_UNAVAILABLE`, also for monitor and soft budgets. | Fail-open with the spool is phase 3. |
| A-42 | 2 | Health heartbeats | The gateway writes heartbeats every 5 seconds for what it saw working in that round: policy sync (snapshot reloaded), ledger (expiry sweep ran), alerting (alert records can be written), gateway (round completed). | PRD names the components but not what a heartbeat must prove. |
| A-43 | 2 | Who sees denial detail (UX-D3) | The denials feed shows full context to everyone who can open the UI, because roles do not exist until phase 5. Agents get only the code and request ID. | UX-D3 default is full context for admin and auditor. |
| A-44 | 2 | Registering a model from the UI | Not built. The phase 1 UI text said it would arrive in phase 2; that was wrong and the text is corrected. Models are added through the seed data. | Not in the brief's phase list. Listed as not built. |
