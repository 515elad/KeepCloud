# Assumptions log

Where the PRD is unclear, the simplest choice that keeps the intent is recorded here. Open decisions (D-xx, SD-xx, UX-Dx) are not decided here: their stated default is implemented and labelled "pending decision" in the UI when the feature appears.

| A-16 | 1 | Independent and subdivision budgets (FR-04) | The limit path of a budget is the budget itself, then each parent reached while the budget below it is a Subdivision. | A-28 | 1 | Unregistered models | Names requested but not registered are kept in their own table and shown as Unregistered. | A-29 | 2 | Approval policy (FR-05, FR-11) | When a project's own budget has the Approval policy, every request from that project is held: budget is reserved, nothing is sent, and the agent gets HTTP 202 with code `APPROVAL_REQUIRED`. Approving or rejecting a hold is phase 5; until then a hold expires after 24 hours and its budget is released. | PRD v1.4 says a HELD reservation "reserves budget" and is the outcome of the approval policy, so a hold must fit the cap. | A-30 | 2 | Unknown models (D-03) | Unknown models are always denied, also for monitor-only budgets. The name is recorded under "Unregistered models". | The owner brief (hard rule 7) says unknown models are denied. | A-31 | 2 | Streaming | Streaming requests (`"stream": true`) are refused with 400 `STREAMING_NOT_SUPPORTED`. | Not in the brief's phase 2. Refusing keeps bypass route B-h closed: no stream, no way to dodge settlement. Listed as not built. |
| A-32 | 2 | Stored result for idempotent replay | The response of a finished request is kept for 24 hours so that a retry with the same key gets the same result. Prompts are never stored. Keys left "in flight" by a crash are removed after 10 minutes. | "Same key, same body returns the stored result" needs the result. SEC-25 (no responses stored by default) is narrowed by this 24-hour copy; the owner may prefer a shorter window. |
| A-33 | 2 | Provider failures | A timeout or connection error after dispatch settles at the reserved amount with usage unknown (PRD). An HTTP error answer from the provider releases the reservation and returns 502; the provider's error text is not passed on. An answer without usage figures settles at the reserved amount. | The PRD defines the timeout case only. A provider that answers with an error did not do the work. |
| A-34 | 2 | Token and policy caching | Credentials are looked up in the database on every request (no 30-second cache), so revocation is immediate. The policy snapshot is reloaded by polling at most every 5 seconds, not by LISTEN/NOTIFY; older than 30 seconds without a successful reload denies everything. | Simplest design that meets "revoked within 30 s" and "block effective within 5 s". The cache can be added if pilot latency needs it. |
| A-35 | 2 | Currency conversion | Model prices are in USD in the demo. A budget in another currency is charged through a stored rate (`fx_rates`, one invented demo rate USD to EUR 0.92). Conversion rounds up. No rate means the request is denied (`FX_RATE_MISSING`). | Without this no EUR budget could be used. PRD v1.4 Section 6 (multi-currency) describes the table. |
| A-36 | 2 | Demo credentials | Demo tokens are derived from the demo seed, so the traffic generator can present them without any token being stored. They are issued when the demo data is loaded, using the database clock (valid 90 days), outside the fixed-clock seed. The gateway refuses to start in production on a database that holds demo data. | A credential's lifetime is real time, but the seeded data set must be identical on every run. |
| A-37 | 2 | Seeded reserved amounts | Each seeded "reserved" amount is backed by a seeded open reservation with a fixed far expiry. They stand for long-running requests and are never swept. | The ledger invariant (a budget's reserved amount equals its open reservations) must also hold for demo data. |
| A-38 | 2 | Demo traffic | The 500 requests, their order and their outcomes are fixed by the seed, and so are the resulting budget totals. Timestamps and request IDs are real. Sending the same run again replays stored results. | The requests go through the live gateway, whose clock is real time. |
| A-39 | 2 | Decision record instead of audit and outbox rows | For an allowed or held request the decision row is written in the reservation's transaction: no record, no dispatch. Requests refused with 401 are counted in metrics only, because no tenant is known. | The audit log is a phase 6 deliverable. |
| A-40 | 2 | Vault | Provider keys come from a `Vault` interface. The MVP implementation returns a fixed non-secret value for the mock provider. No KMS exists. | Hard rule 1: no real credentials. |
| A-41 | 2 | Ledger outage | When the ledger cannot be reached, every request is refused with 503 `LEDGER_UNAVAILABLE`, also for monitor and soft budgets. | Fail-open with the spool is phase 3. |
| A-42 | 2 | Health heartbeats | The gateway writes heartbeats every 5 seconds for what it saw working in that round: policy sync (snapshot reloaded), ledger (expiry sweep ran), alerting (alert records can be written), gateway (round completed). | PRD names the components but not what a heartbeat must prove. |
| A-43 | 2 | Who sees denial detail (UX-D3) | The denials feed shows full context to everyone who can open the UI, because roles do not exist until phase 5. Agents get only the code and request ID. | UX-D3 default is full context for admin and auditor. |
| A-44 | 2 | Registering a model from the UI | Not built. The phase 1 UI text said it would arrive in phase 2; that was wrong and the text is corrected. Models are added through the seed data. | Not in the brief's phase list. Listed as not built. |
| A-45 | 3 | What "ledger unreachable" means | A request falls back to fail-open when its **reservation cannot be written** (connection failure, or the breaker that follows one). Reading policy and credentials is a separate matter: if those cannot be read either, the rules of A-46 and the stale-snapshot rule apply and soon refuse everything. | PRD v1.5 says "when the ledger is unreachable" but does not say whether policy must still be readable. Blocks may never fail open, so policy must be fresh. |
| A-46 | 3 | Credentials during a database outage | When the database is up, every request is checked there (revocation is immediate). When it is down, a credential that was verified in the last 30 seconds is still accepted; any other is refused with 503. | SEC-12 allows "revoked within 30 s". Without this, a full database outage would refuse everything at once and SD-04 could never apply. |
| A-47 | 3 | How long fail-open can last | Two limits apply together. (1) A full database outage: at most about 30 seconds, because credentials (A-46) and the policy snapshot (30-second staleness rule) can no longer be verified. (2) An outage of ledger writes only: until the spool reaches 10,000 records, 100 MB, or its oldest waiting record is one hour old (the proposed caps). | Follows from "blocks always fail closed" and "a stale snapshot denies all". The owner may want to know that a total PostgreSQL outage gives 30 seconds of fail-open, not an hour. |
| A-48 | 3 | Which budgets may fail open | Only a request whose **whole limit path** is monitor or soft with fail mode FAIL_OPEN. A soft project under a hard-limit team or department is refused, because the hard limit above it cannot be checked. Approval budgets are refused. | PRD v1.4 table: hard and approval fail closed. With a hierarchy, the strictest budget on the path decides. |
| A-49 | 3 | Refusal code during an outage | A hard-limit or approval request during a ledger outage gets HTTP 403 `BUDGET_FAIL_CLOSED`. 503 `LEDGER_UNAVAILABLE` remains for the case where the caller cannot even be verified. A full spool gives 503 `FAIL_OPEN_CAPACITY`. | PRD v1.4 names `BUDGET_FAIL_CLOSED` as a structured reason. It is a policy outcome, so 403 under the denial contract. |
| A-50 | 3 | Spool key | The spool is encrypted with AES-256-GCM. The key comes from `KEEPAIR_SPOOL_KEY`; production refuses to start without one. `./run.sh` generates a key into `.env` on the machine (not in git). With no key outside production, a throwaway key is used and spooled records do not survive a restart; `/status` says so. | No KMS exists in the MVP (A-40). | A-51 | 3 | One spool per gateway instance | Each gateway instance has its own spool file and replays it itself. | Simplest correct design; replay is idempotent by record ID, so two instances cannot double count. |
| A-52 | 3 | Idempotency during an outage | Keys cannot be claimed in the ledger. A key already used during the same outage is refused with 409 (the request is not sent twice), but its result is not stored for replay. | Results are stored in the ledger (A-32), which is down. |
| A-53 | 3 | Fail-open events as the audit record | Each replayed request becomes a `fail_events` row, a usage record and a decision record with reason `FAIL_OPEN`. | A-54 | 3 | Acknowledging the banner | One acknowledgement covers all recorded fail-open events so far. It is not possible while fail-open is active or records still wait in the spool. | A-59 | 4 | Finalization of gateway figures | Everything the gateway records is ESTIMATED, also when the provider reported token usage, because the amount comes from KeepAir's own price list. | A-61 | 4 | All-or-nothing files | A file with any invalid row is refused as a whole and nothing is loaded. Reasons name row and column and never repeat cell content. | FR-02: a failing batch is quarantined, not loaded. SEC-28. |
| A-62 | 4 | Revisions | A correction must arrive as a higher revision of the same record key. | A-63 | 4 | Allocation order | Manual assignment, then an exact tag match on team and project (DIRECT), then an allocation rule (INFERRED), then a project-only match (INFERRED, confidence 70, listed for review), else unmatched (tags present) or unallocated (no tags).
